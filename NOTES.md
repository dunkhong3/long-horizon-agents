# Notes

## What this is

The system is a set of agents that audit a mock cloud deployment over a few hundred steps, where the hard part is not any single agent but keeping the whole run coherent while things keep going wrong on purpose. The `v1` tag marks the first core that was built end to end, and everything since builds on that core without changing what it is, as described in the 'Scope' section of [docs/design.md](docs/design.md). Two words come up a lot below. A decoy is a healthy service whose first read returns an old, out-of-date replica count (`lha/world/app.py`, lines 70–73), so it looks broken on first sight but turns out fine when it is read again. An RNG is a random number generator, the usual tool for random choices, and this repo avoids a shared one on purpose (see below).

## What we went deep on

**First, state and context management.** Long agent runs usually break because the context turns into a pile of history, where old errors, stale reads and earlier guesses all compete for attention. In this repo the model never sees history, because each attempt at a task gets a `ContextPacket` built fresh from Postgres (`lha/context.py`, lines 96–109) with the goal, this task, the facts in its scope, the reason its last attempt failed and pointers to what earlier attempts already read, packed from the top down within a token budget (`lha/context.py`, lines 57–93), and within the attempt the model sees only that packet and the results of its own tool calls (`lha/agents/base.py`, lines 153–172). Raw tool output is turned into small, typed facts when it is written, so the prompt grows with the task and not with the run, and a task whose own work outgrows the window is split into batches (`lha/coordinator.py`, lines 482–512).

**Second, failure detection and recovery.** Faults are injected everywhere on purpose and reproducibly, meaning they are seeded so the same seed gives the same faults. They include HTTP 500, 503 and 429 responses, timeouts, empty 'successful' responses, stale reads, a host that is down for a whole round, malformed and fabricated model output, workers that die or hang in the middle of a task, a coordinator that crashes halfway through committing a result, and, with `--kill-at`, a hard crash of every process (`lha/world/app.py`, lines 27–46; `lha/agents/base.py`, lines 110–145; `lha/agents/worker.py`, lines 82–121; `lha/coordinator.py`, lines 161–206; `lha/run.py`, lines 333–340). Each kind of fault has a specific mechanism that catches it, and every run is scored against the planted answer (`lha/scoring.py`, lines 30–63).

**Lastly, we measured both against a naive baseline.** The baseline is one agent whose prompt is its whole history, run on the same worlds with the same faults (`lha/baseline.py`), and on 60 hosts its prompts average about 6,900 tokens against about 320 for the system, it names a decoy in every run unless it re-reads a mismatch, and once its history is cut to a 2000-token window it repeats about 1,200 reads per run and runs out of steps in 9 runs out of 10 ('The benchmark' in [docs/design.md](docs/design.md)). The fake model reads a long prompt perfectly, which a real model does not, so these gaps are the smallest they would be.

## Decisions we are most confident about

**The coordinator is plain code and not an LLM.** LLMs propose and code decides, and the coordinator is the only writer of facts and of the plan (`lha/coordinator.py`), so there is one source of truth and no agent can talk the system into a wrong state.

**We never trust a claim that code can check.** Every fact a worker reports cites the tool-call event it came from, and the coordinator checks the value against that event's raw response before it accepts anything, and checks a copy fetched by pointer against its original (`lha/coordinator.py`, lines 236–261, 401–442 and 924–929), so fabricated output is rejected and not believed.

**Two independent reads must agree before a drift counts.** The newest read is not automatically right, and the decoys show why, because their first read is stale and only a majority of reads settles it (`lha/coordinator.py`, lines 337–371).

**Postgres is the only shared state, and four small tools inside it do most of the work.** These are `FOR UPDATE SKIP LOCKED` for the task queue (`lha/db/crud.py`, lines 112–125), an `attempt` number used as a fencing token for leases, which lets a slow worker find out it has been replaced (`lha/db/crud.py`, lines 133–168), a partial unique index for 'one current fact per key' (`lha/db/models.py`, lines 102–111), and an advisory lock that keeps a session to one coordinator even while a crashed one is being replaced (`lha/coordinator.py`, lines 104–148).

**Each accepted result is one transaction, covering the facts, the follow-up tasks and the decision log.** A crash cannot leave half a decision behind (`lha/coordinator.py`, lines 161–234), which is why restarting the coordinator, and `--resume`, are simple, because nothing important lives in memory.

**Follow-up tasks are only created from accepted results.** Apart from the starting tasks, the report task and work re-opened after a stall, every task comes from an accepted result, so failed work cannot flow downstream, because nothing downstream is ever created from it (`lha/coordinator.py`, lines 289–306 and 514–550).

**Faults are seeded on stable names and not on ids or a shared RNG.** The roll is a hash of the seed, the `task_key`, the attempt and the call number (`lha/faults.py`, lines 19–27), so a seed gives the same faults across processes and across runs, whereas a shared RNG would give different results depending on which process happened to ask first.

## What is still not built

The code does not use `LISTEN/NOTIFY`, so idle workers and the coordinator poll Postgres every 50 ms (`lha/config.py`, line 45), and it does not split one session between several coordinators, so the single coordinator is the first thing that would limit throughput, as described under 'Limits and scaling' in the design doc. The code does not have `depends_on` between tasks, because every task is created only once its inputs exist, so nothing ever waits on another task. The mock world stays simplified, because a read that matches the registry is trusted after one read and stale reads only ever create false drifts and never hide real ones. Lastly, there is no real model, and every agent runs on a fake one through Pydantic AI's `FunctionModel`, so a real model behind the same `Agent` interface, with the fake one kept for reproducible tests, is the natural step after the rest.

## How we used coding tools

We built this with Claude Code, and the way of working had three parts. First, the design came before any code, in `docs/design.md`, and we went through several review passes, each of which found real gaps, such as faults keyed on ids not being reproducible, made-up facts not actually being caught, a 'list all hosts' endpoint making the hidden hosts pointless, and `depends_on` turning out to be unnecessary. Second, the code was written against that document, with `CLAUDE.md` holding the working rules and the architecture rules so that every session followed the same design. Lastly, we ran the system a lot, with full runs across many seeds, fault rates, goals and crash rates plus crash-and-resume runs, and those runs found real bugs. One early run found the drift after only 8 of 20 hosts because one worker raced down the chain of documents while another was stuck on timeouts, which we fixed by hanging the chain below the deepest hosts (`lha/world/model.py`, lines 97–115). A 'find all drifts' run declared the goal met while a failed batch had left part of a host unread, which we fixed by recording what each host lists and checking all of it was read (`lha/coordinator.py`, lines 713–766), and the same runs showed that a packet allowed to fill the whole window left no room for the attempt's own work, which is why the window is now shared between the packet and the attempt (`lha/config.py`, lines 36–38).
